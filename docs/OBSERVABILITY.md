# PropRelay — Observability & Reliability Architecture

## 1. Overview

PropRelay implements a production-style local, zero-cloud observability and reliability architecture. Observability in PropRelay operates across three distinct planes:

1. **Telemetry & Metrics Plane (`MetricsStore`)**: Monotonic latency tracking, turn metrics, workflow KPIs, and percentile computation guarded by statistical sample size validation.
2. **Error Taxonomy & Reliability Plane (`ErrorTaxonomy`)**: Strict categorization of all operational exceptions into structured, actionable error records with recovery actions.
3. **Audit & Diagnostics Plane (`EventJournal` & `diagnostics`)**: Tamper-evident hash-chained domain event logging, event replay, and environmental pre-flight health diagnostics.

## 2. Latency & Telemetry Provenance

All latency measurements recorded across turns are explicitly labeled with their provenance:

| Provenance Tag | Source | Measurement Method |
| :--- | :--- | :--- |
| `LIVEKIT_NATIVE` | LiveKit Agents Core | Framework timers via `MetricsCollectedEvent` |
| `CUSTOM_APP_TIMER` | `proprelay.agent.session` | Python `time.perf_counter()` monotonic timers |
| `DOMAIN_EVENT_TS` | `proprelay.events.schemas` | Monotonic UTC ISO 8601 timestamps on event creation |
| `DERIVED` | Arithmetic Delta | Calculated differences across stage boundaries |

### Minimum Sample Threshold Guard

Percentiles ($p50$, $p90$, $p99$) can produce misleading or fabricated figures when sample counts are insufficient. PropRelay enforces an explicit sample size guard:

- Threshold: $N \ge 3$
- If $N < 3$, the system returns: `"insufficient samples (N=<count>)"`


## 3. Structured Error Taxonomy

Rather than relying on unformatted stack traces or generic error strings, all pipeline errors are captured into a typed `StructuredError` envelope:

```json
{
  "error_id": "err-34a873f1",
  "category": "TOOL_EXECUTION",
  "code": "SLOT_UNAVAILABLE",
  "message": "The requested showing slot 2026-10-02T10:00:00 is already reserved.",
  "severity": "MEDIUM",
  "recoverable": true,
  "recovery_action": "PROMPT_ALTERNATIVE_SLOT",
  "session_id": "sess-8b9a1c4",
  "timestamp": "2026-09-23T04:12:00.123Z",
  "context": {
    "property_id": "prop-001",
    "slot_id": "slot-101"
  }
}
```

### Error Categories & Standard Recovery Actions

| Category | Typical Codes | Severity | Recoverable | Default Recovery Action |
| :--- | :--- | :--- | :--- | :--- |
| `STT_FAILURE` | `EMPTY_AUDIO`, `INFERENCE_TIMEOUT` | Low / Medium | Yes | `REASK_USER` |
| `LLM_FAILURE` | `CONTEXT_OVERFLOW`, `OLLAMA_TIMEOUT` | High | Yes | `RETRY_WITH_TRUNCATION` |
| `TTS_FAILURE` | `KOKORO_UNREACHABLE`, `SYNTH_ERROR` | High | Yes | `FALLBACK_SILENT_ACK` |
| `TOOL_EXECUTION` | `SLOT_UNAVAILABLE`, `INVALID_DATE` | Medium | Yes | `PROMPT_ALTERNATIVE_SLOT` |
| `WEBRTC_TRANSPORT` | `DATA_CHANNEL_CLOSED`, `BUFFER_FULL`| Medium | Yes | `RETRY_TRANSMIT` |
| `VALIDATION_POLICY`| `NO_PENDING_ACTION`, `STALE_ACTION`| Low | Yes | `CLARIFY_INTENT` |
| `SYSTEM_RESOURCE` | `CUDA_OOM`, `PORT_CONFLICT` | Critical | No | `ABORT_SESSION` |

## 4. Observability REST Endpoints

The unified FastAPI server exposes dedicated operational telemetry endpoints:

- `GET /api/metrics/summary`: Returns aggregate metrics across all sessions (turn count, average latency by stage, guarded percentiles, error rate).
- `GET /api/sessions/{session_id}`: Returns turn-by-turn latency records, workflow state transitions, and structured errors for a specific session.
- `GET /api/workflows/{workflow_id}`: Returns the complete execution history, tool invocations, and confirmation statuses for a specific workflow.
- `GET /api/events`: Replay endpoint for the append-only event journal with optional filtering by `event_type`, `session_id`, or `time_range`.
- `GET /api/evaluations/latest`: Returns the most recent behavioral evaluation report generated by the evaluation runner.

## 5. System Diagnostics CLI (`proprelay.diagnostics`)

PropRelay includes an automated pre-flight diagnostics utility:

```powershell
python -m proprelay.diagnostics
```

The diagnostics engine verifies:
1. **Python Environment**: Version $\ge 3.12$, virtual environment isolation.
2. **GPU & CUDA**: PyTorch CUDA availability, device name, compute capability.
3. **STT Engine**: `faster-whisper` CTranslate2 model loading and CUDA tensor allocation.
4. **Node & Frontend**: Node.js $\ge 20$, pnpm availability, `frontend/dist` build status.
5. **LiveKit Server**: TCP port reachability on port 7880, health endpoint check.
6. **Ollama LLM**: Port 11434 reachability, `qwen2.5:7b` model presence.
7. **Kokoro TTS**: Port 8880 reachability, ONNX runtime verification.
8. **Catalog Fixtures**: Integrity and parsing of `data/listings.json` and `data/showings.json`.
